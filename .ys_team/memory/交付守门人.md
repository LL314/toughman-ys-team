# 交付守门人 经验记忆

## evidence 质量要求（2026-04-15）

**错误模式**：evidence 文件只写"验收通过"等成功结论，不记录执行过程中遇到的 gap 和处理方式。

**正确做法**：evidence 必须同时包含：①成功结论及对应验证命令输出，②链路中发现的 gap 及实际处理方式（即使是人工兜底也要写明）。这样后续才能区分"机制真正可用"和"靠人工补救通过"。

**适用场景**：所有 spec 的 QA 和 close 阶段；尤其是首次验证新机制（如 full-auto 模式）时。

## 多 spec 合并发版的处理模式（2026-05-07）

**场景**：一个 release（如 0.6.0）由 N 个 spec 组成时，前序 spec 不应单独走完 close 触发 npm publish，否则会形成 N-1 次中间发版，污染 release 线。

**正确做法**：前序 spec 完成 spec-work + qa 后停在 `docs/specs/active/`，状态写明"等下一个 spec 一起 close"；最后一个 spec 的 close 阶段统一执行 npm publish + 合回 main + tag + push，并在归档时把所有合并发版的 spec 一起移到 archive。

**关键约束**：rules.md 第 67 行"close 前必须 npm publish"在多 spec 合并发版场景下应理解为"release 单元"层面的约束，不是"单个 spec"层面。spec.md 的 AC 必须显式写明"qa PASS 后不进 close"，否则 full-auto 链路会自动触发 close 链路并尝试发版。

**适用场景**：用户在路由阶段明确说"两/多个 spec 合并发版"时；spec 划分以风险隔离为目的而非 release 单元为边界时。


## 工作流更新与独立 npm 发布（2026-11-02）

**读取入口**：后续更新工作流、打包、发布或升级本仓时，先读 [工作流更新与 npm 发布 SOP](../../docs/project/npm-publish.md)。完整操作只在该文档维护，本记忆保留非显然教训。

- **身份与权限分开**：MIT 再分发许可、原 npm 包名所有权、自己的 token 发布权限是三件事；本仓包名固定为 `toughman-ys-team`，CLI 仍是 `ys-team`。
- **不从错误猜根因**：Chrome 登录不能证明 CLI 登录；Bypass 2FA 不证明直接发布权限；E404 不能证明 scoped 包名不可用。使用 `npm whoami`、明确错误码和 token 权限核对。
- **政策有时效**：旧 token 的 E_STAGE_REQUIRED 表示不能直接发布，不表示 staged 路径不能创建新包；执行前核对 SOP 中的官方文档。
- **隐藏输入必须确认就绪**：曾因未观察终端状态重复输入，导致凭据落入命令行；也曾误用被用户更新的剪贴板。使用明确提示、输入一次、重新观察，临时认证配置在结束时清理，不保存 token 正文。
- **成功需双重证据**：publish 退出码 0 后可能仍在处理；只有 registry 版本、latest 和 tarball 校验一致才算上线。Git main、tag、push 另行核对。

**已验证案例**：`toughman-ys-team@1.0.4` 于 2026-11-02 发布，registry tarball 与本地一致，main 和 v1.0.4 tag 已推送。下次重新读取当前状态，不把此版本当作永久最新值；详见 [发布记录](../../docs/specs/archive/20261030-toughman-package-rebrand/work.md)。
